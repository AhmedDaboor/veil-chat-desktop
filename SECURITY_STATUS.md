# Security status — desktop Matrix client

Status: functional implementation under security validation; not production ready.

## Implemented controls

- .NET 10/Avalonia starts an explicitly configured Rust worker; JSON Lines IPC v2 is bounded to 64 KiB, strict UTF-8/JSON, typed by method, single-flight, and correlated by request UUID. Unexpected output, invalid response shapes, process exit, cancellation, and timeouts invalidate and clean up the worker.
- The official Matrix Rust SDK is pinned to 0.19.1 with SDK E2EE and encrypted SQLite storage. Login/session restore, synchronization, encrypted direct-room discovery/creation, text history, send, and logout are routed through the worker.
- Every Matrix operation requires the worker's Tor supervisor to be ready. Tor starts only from an explicitly configured executable and app-owned empty defaults/config files, so system or user torrc settings cannot alter the supervised listeners or enable relay behavior. The worker authenticates with SAFECOOKIE, takes ownership of its Tor control connection, checks bootstrap progress and the exact loopback SOCKS listener, and grants the Matrix client a `VerifiedTorRoute` only after those checks pass.
- Matrix HTTP uses `socks5h`, an explicit proxy, and `.no_proxy()` to prevent environment/system proxy bypass. There is no direct-network fallback. Requests fail closed if the worker cannot establish or revalidate the Tor route.
- The worker creates DMs through the SDK with E2EE enabled and returns room-creation success only after the SDK verifies encryption. It filters rooms and refuses history/send unless the SDK reports room encryption. C# response validation requires `encrypted: true` and known encryption before presenting a room for sending. For each one-to-one room, the UI also displays the SDK's cached peer cross-signing identity state, including unknown, unverified, previously verified, and identity-change violation states. It never infers verification when the SDK has no identity.
- The worker lists invitation metadata from the SDK and accepts only invited rooms marked direct whose encryption state is known and enabled. After joining, it syncs, rechecks encryption, and requires exactly two active members including the local user before recording the room in the recipient's `m.direct` account data. It attempts to leave on a failed post-join check. The UI disables acceptance for invitations that lack the pre-join direct/encryption flags and can load decrypted message history after a recipient joins. This is a membership-count guard, not identity verification.
- Peer cross-signing verification uses the pinned SDK's SAS flow. The worker permits one flow at a time, only for a peer in an encrypted one-to-one room, requests SAS without QR, synchronizes state through the Tor-gated Matrix client, and returns the SDK's SAS values. The UI requires a deliberate confirmation after out-of-band comparison; the SDK identity status is refreshed and shown only as verified after it reports verification.
- Login passwords are held transiently and never saved. Session tokens and the SDK-store passphrase are written to Windows current-user DPAPI or Linux Secret Service. Windows protected-session reads are bounded to 48 KiB. Secure-store failures block retained login; there is no plaintext fallback. Worker stdout carries only protocol frames; stderr is discarded, and application errors are static codes/messages without credentials or message bodies.

## Explicit limitations and release blockers

- This host has no Tor executable and no Linux Secret Service client. A real-worker integration test verifies that every Matrix network method, including invitation listing and acceptance, is denied when Tor is not configured, but successful SAFECOOKIE authentication, bootstrap, SOCKS routing, Matrix login, E2EE send/receive, DNS behavior, and Tor-only egress have not been exercised against live services. Do not describe Tor or end-to-end messaging as runtime verified.
- The app initiates peer SAS verification, but does not accept incoming verification requests, expose per-device verification or QR, or automate identity recovery. The peer must accept the request in a compatible Matrix client. Users must compare all seven emoji or all three number groups over a trusted separate channel and cancel if any differ. Only the SDK's resulting cross-signing status is displayed; launching or confirming a flow alone never marks a peer verified.
- `matrix-sdk 0.19.1` has a direct, unconditional dependency on `anymap2 0.13.0`. [RUSTSEC-2026-0319](https://rustsec.org/advisories/RUSTSEC-2026-0319.html) is INFO/unmaintained, reports no vulnerability, and lists no patched version. The pinned SDK is the latest tagged official release checked on 2026-10-16 ([official release list](https://github.com/matrix-org/matrix-rust-sdk/releases)); its [published manifest](https://docs.rs/crate/matrix-sdk/0.19.1) declares `anymap2` as a normal dependency. Supported feature selection does not remove the dependency. The advisory is not suppressed or bypassed. Production release needs an upstream stable resolution or explicit supply-chain risk review.
- Linux login requires `secret-tool` plus a usable, unlocked Secret Service. Windows session storage uses DPAPI. These paths have not both been exercised on their native desktop OS in this environment.
- Linux worker data directories are set to owner-only permissions. On Windows the Tor cookie/data directory relies on inherited NTFS ACLs; the app recommends the default per-user LocalApplicationData location but does not harden a custom directory ACL.
- Packaging scripts create unsigned, framework-dependent Windows/Linux application packages and place the matching worker beside the app. They do not bundle Tor or create signed installers. Automatic upgrades, backup/recovery, incoming/per-device verification, and a native Linux .NET test run are not provided. The current .NET tests ran with Windows .NET 10.0.400 through WSL interop.
- Basic one-to-one text only. Groups, calls, attachments, push notifications, analytics, advertising, and account recovery are out of scope.

## Configuration

No executable discovery or alternate transport is used. Native launches require an absolute `VEIL_CHAT_WORKER_EXECUTABLE` and `VEIL_CHAT_TOR_EXECUTABLE`; `VEIL_CHAT_DATA_DIRECTORY` may select an absolute private data path. Windows-to-WSL launches require explicit Linux worker path, WSL distribution, Linux data directory, and Linux Tor executable. Missing or invalid configuration blocks network operations.

## Verification scope

Rust unit tests cover IPC parsing/framing including bounded peer-verification identifiers, isolated Tor command configuration, Tor protocol helpers, SAFECOOKIE authentication and a fake Tor executable process lifecycle, SOCKS listener matching, a real reqwest SOCKS5h request that verifies remote DNS and proxy failure, and direct-room/invite membership and encryption guards. .NET tests cover protocol and SAS response validation, worker lifecycle and concurrency, bounded DPAPI session storage, real worker IPC, and real-worker checks that every Matrix network and verification method is denied without Tor. The opt-in [live test runner](scripts/live-matrix-smoke.py) exercises the worker against an installed Tor and test Matrix accounts; its [runbook](docs/live-matrix-test.md) separates SDK-operation results from the additional evidence needed for recipient decryption and process-level egress observation. The live runner and SAS flow have not been exercised against live accounts here. Automated tests and the runner do not establish actual Tor egress, live Matrix behavior, anonymity, completed peer identity verification, or production readiness. See [README.md](README.md) and [docs/worker-ipc-v2.md](docs/worker-ipc-v2.md) for commands and the current protocol contract.
